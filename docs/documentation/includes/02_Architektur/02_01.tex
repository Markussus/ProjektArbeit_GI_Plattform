\subNsection{1}{Technologiestack}{Richard Schröder}
Die Anwendung wurde als eine Client-only Webanwendung umgesetzt, d. h. es gibt kein Backend das Funktionen ausführt, außer dem Bereitstellen der Seite selbst. Deshalb wurden nur Frontend-Technologien verwendet. Den Kern der Seite bildet \verb|React 19| mit dem \verb|React Router|, welcher zusätzlich Lazy Loading für bessere Performance ermöglicht. Die Logik selbst wurde in \verb|TypeScript| entwickelt. Der lokale Entwicklungsserver wurde mit \verb|Vite| betrieben, was auch einen optimierten und statischen Build der Seite für das spätere Deployment generiert. Außerdem werden über \verb|vitest| die Unit-Tests abgebildet.

Das Styling der Seite basiert auf \verb|Tailwind CSS 4| und den damit erstellten Utility-Klassen der einzelnen React-Komponenten sowie diversen CSS-Variablen um z. B. Farben für die ganze Anwendung einheitlich zu halten. Mit \verb|shadcn/ui| wurde die grundlegende Designbasis erstellt und \verb|Tailwind CSS| um einige Komponenten und Theme-Strukturen ergänzt. Die Icons wurden per \verb|Lucide React| direkt als React-Komponenten zur Verfügung gestellt.

Für einige globale Benutzeroberflächenzustände kommt \verb|Zustand| zum Einsatz. Damit werden die Einstellung der Seitenleiste sowie die gewählte Darstellung zentral verwaltet, zusätzlich wird die Theme-Einstellung im Local Storage gespeichert, sodass sie nach einem erneuten Aufruf der Anwendung erhalten bleibt. Fachliche Zustände der einzelnen Simulatoren werden hingegen überwiegend lokal in den jeweiligen Komponenten und zugehörigen Domänenmodellen geführt.

Für die Internationalisierung wurde \verb|i18next| bzw. \verb|react-i18next| eingesetzt, somit kann die gesamte Anwendung einfach in verschiedene Sprachen übersetzt werden.

Im Java-Bereich wurde zudem \verb|monaco| als Editor eingebunden, der Java Code wird anschließend mit der \verb|TeaVM| direkt im Browser kompiliert und ausgeführt.

Zur statischen Analyse des TypeScript-Codes wird \verb|fallow| eingesetzt. Die bereitgestellten Skripte prüfen insbesondere ungenutzten Code, Duplikate sowie weitere Qualitäts- und Abhängigkeitsaspekte (\verb|fallow audit|). Die Ergebnisse dienen als Grundlage, um nicht mehr benötigte Bestandteile und mögliche Redundanzen im Quellcode zu erkennen.

Die Versionsverwaltung erfolgt mit Git, das zentrale Repository und die automatisierten Abläufe werden über das THWS GitLab organisiert. GitLab CI führt unter anderem Formatierungs- und Lint-Prüfungen (\verb|eslint|), Unit-Tests (\verb|vitest|), den Build sowie End-to-End-Tests (\verb|playwright|) aus. Die konkrete Umsetzung der CI/CD-Pipeline und des GitLab Runners wird in Kapitel~\ref{5_1_QS} behandelt.
